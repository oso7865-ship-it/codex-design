# Vue UI Polish

> 목적: Vue 3 인터페이스가 자주 사용해도 편안하고, 즉각 반응하며, 프로젝트 전체와 일관되게 느껴지도록 검토·개선한다. 장식보다 목적, 빈도, 가독성, 접근성, 성능을 우선한다.
> 사용 위치: **Vue 3 프로젝트 전용(스택 한정 스킬, `01.SKILL_TEMPLATE.md §2-2`)**. 코드 스킬.
> 출력물: 리뷰 표(위치/현재/제안/이유/중요도) 또는 검증된 UI 개선 코드
>
> 파생 고지: 이 스킬은 Emil Kowalski의 `Skills for Design Engineers`에서 공개한 디자인 엔지니어링·모션 원칙을 MIT 라이선스에 따라 Vue 중심으로 재구성한 파생 작업이다. 저작권 및 허가 고지는 `skills/vue-ui-polish/LICENSE`에 보존되어 있다.

## 0. Harness Control Rule

- 이 스킬은 `00.HARNESS_RULES.md`의 하위 모듈이다. **Vue 3 프로젝트에서만 발동하는 스택 한정 스킬이며, 해당 스택이 아닌 프로젝트에서는 이 스킬의 존재 자체를 무시한다(ADR-043).**
- 충돌 시 이 스킬의 절차를 중단하고 `00.QUICK_REF.md`와 `00.HARNESS_RULES.md §3` 우선순위에 따라 상위 규칙을 따른다. 위험 작업 WARN은 사용자 확인 전 스킬 단독으로 진행하지 않는다.

---

## 1. Trigger

- Vue 3 컴포넌트의 UI/UX, 반응형 배치, 상호작용을 검토하거나 개선할 때
- "어색하다", "AI가 만든 것처럼 보인다", "모바일과 PC에서 자연스럽게 다듬어 달라"는 요청을 받았을 때
- 버튼·모달·드롭다운·토스트·목록 전환의 CSS 애니메이션·Vue Transition을 추가·개선·리뷰할 때

---

## 2. Do Not Trigger

- Vue 3가 아닌 프로젝트(React, 순수 HTML 등 — 이 스킬의 존재를 무시한다)
- 화면 흐름·정보 구조의 설계 자체가 필요한 경우(`skills/ui-ux-design/SKILL.md`가 소유)
- 디자인 개선을 명분으로 비즈니스 로직·API 계약·인증 흐름을 바꿔야 하는 경우
- 상위 하네스 규칙과 충돌하는 작업인 경우

---

## 3. Required Inputs

| 입력물 | 필요 이유 |
|---|---|
| 프레임워크 버전, 스타일 방식(Tailwind/CSS Modules/scoped 등), UI·모션 라이브러리, 기존 디자인 토큰 | 기존 체계 재사용 판단 |
| 대상 화면의 목적, 중요 정보, 주요 행동, 사용 빈도 | 애니메이션 필요성·강도 판단 |
| 주 사용 환경(별도 설명 없으면 모바일 우선, PC 확장) | 반응형 판단 기준 |

## 4. Procedure

1. **작업 범위 결정** — 사용자의 동사를 먼저 구분한다(`skills/intent-to-implementation/REFERENCE_INTENT_ROUTING.md`와 같은 원칙).
   - 검토·진단·설명: 파일을 읽고 근거 있는 문제와 개선 방향만 제시한다. 코드를 수정하지 않는다.
   - 수정·개선·구현: 기존 구조와 토큰을 조사하고 요청 범위 안에서 수정한 뒤 검증한다.
   - 아이디어 탐색: 애니메이션 후보 대부분을 기각하는 보수적 태도로, 정말 도움이 되는 기회만 제안한다.
   - 시안 비교: 사용자가 여러 버전을 요청할 때만 격리된 화면에서 3개 이하의 뚜렷이 다른 방향을 만들고 선택을 기다린다. 선택 전에는 운영 화면에 반영하지 않는다.
2. Required Inputs의 항목을 실제로 확인한다(버전, 토큰, 라이브러리, 사용 환경, 화면 목적).
3. **레이아웃 → 가독성 → 상태 표현 → 입력 피드백 → 모션 → 접근성 → 성능** 순서로 검토한다.
4. **애니메이션 필요성 증명**: 피드백 / 공간적 연결 / 상태 표시 / 시각적 연결 / 설명 / 드문 완료의 절제된 즐거움 — 이 중 하나를 명확히 말할 수 있을 때만 움직임을 사용한다. 사용 빈도가 높을수록 줄인다(하루 100회 이상·키보드 중심 행동은 제거, 빈번한 토글은 거의 느껴지지 않게, 가끔 쓰는 모달·드로어는 짧은 표준 모션, 최초·온보딩은 즐거움 허용).
5. **모바일과 PC를 각각 판단한다**: 모바일에서 hover를 주요 수단으로 쓰지 않고, 터치 대상 크기·간격을 먼저 확보하고, PC hover 모션은 `hover: hover`+`pointer: fine` 조건 안에서만, 좁은 화면은 축소 대신 줄바꿈·재배치·우선순위 조정.
6. Vue 구현을 다룰 때는 `skills/vue-ui-polish/REFERENCE_VUE_PATTERNS.md`, 애니메이션 값·모션 심사는 `skills/vue-ui-polish/REFERENCE_MOTION_RULES.md`, 사용자가 움직임의 명칭을 모를 때만 `skills/vue-ui-polish/REFERENCE_ANIMATION_VOCABULARY.md`를 읽는다.
7. 기존 컴포넌트 구조와 라이브러리를 재사용한다. 작은 효과 때문에 새 의존성을 추가하지 않는다.
8. 수정했다면 관련 빌드·린트·테스트를 실행하고, 화면 검증 수단이 있으면 `skills/browser-qa/SKILL.md`로 모바일·PC 크기를 실측 기록한다.

## 5. Quality Gate

| 판정 | 기준 |
|---|---|
| PASS | 검토 요청이면 리뷰 표(위치/현재/제안/이유/중요도)와 우선 수정 1건·모션 제외 대상이 제시됨. 수정 요청이면 기존 토큰·라이브러리 재사용이 확인되고 빌드·검증이 수행됨. 애니메이션마다 필요성 근거(피드백/공간 연결/상태/설명 등)가 있음 |
| WARN | 개선은 유효하나 reduced-motion 대응·터치 대상 크기 등 접근성 확인이 누락됨, 또는 모바일/PC 중 한쪽만 확인됨 — 보완 전 완료 보고하지 않음 |
| FAIL | Vue 3가 아닌 프로젝트에 적용함, 검토 요청인데 코드를 수정함, 디자인 명분으로 비즈니스 로직·API 계약·인증 흐름을 변경함, 근거 없는 새 의존성을 추가함 |

## 6. Output Format

```md
## Vue UI Polish 결과

| 위치 | 현재 | 제안 | 이유 | 중요도 |
| --- | --- | --- | --- | --- |

- 가장 먼저 고칠 한 가지:
- 오히려 애니메이션을 넣지 말아야 할 부분:
- (구현 작업이었다면) 변경 내용과 검증 결과:
- PASS/WARN/FAIL:
```

중요도 판단 — **높음**: 기능 이해, 모바일 사용, 접근성, 프레임 저하, 반복 사용감에 직접 영향 / **중간**: 눈에 띄는 일관성·피드백·공간 연결 문제 / **낮음**: 핵심 경험을 해치지 않는 미세한 완성도.

문제가 없으면 억지로 지적하지 말고 이미 적절하다고 말한다.

## 8. Anti-Patterns

- `transition: all` 사용, UI 진입에 `ease-in`, `scale(0)` 등장, 이유 없는 300ms 초과 UI 모션
- 이동 모션에 `prefers-reduced-motion` 대응 없음, 모바일에서 hover가 있어야만 정보를 알 수 있는 구조
- 프레임마다 `width`/`height`/`margin` 같은 레이아웃 속성을 갱신하는 구현
- 단지 멋있다는 이유로 자주 보는 요소를 움직이기
- 기존 Tailwind/CSS Modules/scoped CSS 방식을 혼합하기
- 단일 색상이나 그림자만 바꾼 시안을 서로 다른 디자인 방향이라고 부르기
